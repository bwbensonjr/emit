## Purpose

Defines which of the repository's hand-authored Scheme files are mechanically formatted,
the single declared configuration that decides their layout, the two doors that format and
check them, the commit-time gate that keeps them formatted, and the evidence a whole-tree
reformat must produce to show it changed no program's meaning. Formatting is treated as a
property of the tree rather than a per-file negotiation, and the formatter is a *developer*
tool: nothing in the project's build or test path may require it.

## ADDED Requirements

### Requirement: One declared covered set names every formatted file

The project SHALL declare, in exactly one place, the set of files the formatter owns. The
covered set SHALL contain only hand-authored Scheme sources of the compiler, the runtime
library, and the build tools. A file SHALL be either covered or explicitly outside the set;
there SHALL be no third state in which a file is formatted opportunistically.

Generated Scheme SHALL be outside the covered set. A generated file's bytes are decided by
its generator and pinned by a byte-identical guard, so its formatting belongs to the
generator, not to the formatter. Vendored code, imported reference material, demonstration
programs, and test programs SHALL likewise be outside the set.

Adding a hand-authored Scheme source to the covered components SHALL bring it into the
covered set without a separate edit to a list of file names: the declaration SHALL be
stated as covered locations and named exclusions, not as an enumeration of every file.

#### Scenario: The covered set is the authored compiler, runtime, and tools

- **WHEN** the covered set is resolved against the working tree
- **THEN** it contains the hand-authored Scheme sources under `src/` (including
  `src/passes/`), the hand-authored `lib/**/*.sld` libraries, the Scheme tools under
  `tools/`, and `emit-libs.scm`
- **AND** it contains no file under `demos/`, `test/`, `historical/`, `build/`, or a
  vendored directory

#### Scenario: A generated source is excluded and stays excluded

- **WHEN** the covered set is resolved and a Scheme file is generated by a project
  generator and guarded by a byte-identical check
- **THEN** that file is not in the covered set
- **AND** running the formatter over the covered set leaves that file byte-for-byte
  unchanged

#### Scenario: A new authored pass joins the set without editing a file list

- **WHEN** a new hand-authored Scheme source is added under a covered location
- **THEN** it is in the covered set on the next resolution, with no edit to the declaration

#### Scenario: An unformattable file is a defect, not an exclusion

- **WHEN** a file in the covered set cannot be formatted
- **THEN** the failure is reported as an error rather than resolved by removing the file
  from the covered set

### Requirement: One declared configuration decides layout

The project SHALL carry a single explicit formatter configuration file, and every
invocation of the formatter on the covered set SHALL resolve its layout from that file.
The configuration SHALL declare the page width, and SHALL declare styles for the project's
own macros so that the compiler's pattern-matching passes lay out under a named rule
rather than a generic fallback. No layout decision affecting the covered set SHALL depend
on an implicit search of the working directory, the parent directories, the home
directory, or the environment.

Each group within the covered set SHALL be formatted under the dialect its sources are
written in. The dialect SHALL be selected by the declared group a file belongs to, never
inferred from its file extension.

The formatter version SHALL be pinned and recorded. The formatter's layout is not a
stable interface; an unrecorded upgrade would silently invalidate the formatted tree.

#### Scenario: Layout comes from the project configuration

- **WHEN** the formatter runs over the covered set
- **THEN** it is given the project's configuration file explicitly
- **AND** the resolved width and styles are those the file declares

#### Scenario: R7RS libraries and host programs get their own dialects

- **WHEN** the covered set is formatted
- **THEN** the hand-authored `lib/**/*.sld` R7RS libraries are formatted under the R7RS
  dialect
- **AND** the compiler and tool sources that run on the bootstrap host are formatted under
  their own declared dialect
- **AND** no file's dialect is decided by whether it is named `.scm` or `.ss`

#### Scenario: The pinned formatter version is recorded and checked

- **WHEN** the formatting doors run and the available formatter's version is not the
  pinned one
- **THEN** the mismatch is reported, naming both the pinned and the found version, rather
  than silently producing layout the tree was not formatted with

### Requirement: Two doors format and check, and they narrate

The project SHALL provide one door that rewrites the covered set in place and one door
that answers the same question without writing anything. The checking door SHALL exit
non-zero when any covered file would change, and SHALL distinguish that outcome from a
usage or I/O failure, so an automated caller can tell "this tree is unformatted" from
"this invocation is wrong".

Both doors SHALL conform to the project's tooling-observability conventions: each SHALL
announce the action it performs, name the covered set it resolved, and report the counts
and elapsed time that make the run observable. Narration SHALL go to standard error.

Running either door over an already-formatted tree SHALL write nothing — no file
modification times SHALL change — so that formatting never provokes a rebuild.

#### Scenario: The checking door fails on an unformatted tree

- **WHEN** the checking door runs and at least one covered file would change
- **THEN** it exits non-zero
- **AND** it names each file that would change

#### Scenario: The checking door distinguishes a broken invocation

- **WHEN** the checking door cannot run — the formatter is absent, the configuration is
  malformed, or a covered path cannot be read
- **THEN** its exit status differs from the status it uses for "a file would change"
- **AND** the reported message names the cause

#### Scenario: A run reports what it did

- **WHEN** either door completes
- **THEN** its output names the action, the number of files considered, the number that
  changed or would change, and the elapsed time

#### Scenario: A formatted tree is untouched

- **WHEN** the formatting door runs twice in succession
- **THEN** the second run rewrites no file and changes no modification time

### Requirement: The commit gate checks staged files and never blocks on an absent formatter

The project SHALL provide an opt-in commit-time gate, installed by an explicit action
rather than by cloning the repository. The gate SHALL check only the covered files that
are staged for the commit, not the whole covered set: whole-set checking costs minutes and
would make committing unusable.

The gate SHALL take its covered-set membership and its dialect assignment from the same
single declaration the doors use, so a file cannot be gated under one policy and formatted
under another.

When the formatter is not available, the gate SHALL skip and permit the commit, reporting
that it skipped and why. The project's compiler builds the formatter, so requiring the
formatter to commit to the compiler would make the project unbuildable from a clean
environment.

#### Scenario: A staged unformatted file blocks the commit

- **WHEN** the gate runs and a staged file in the covered set would change
- **THEN** the commit is rejected
- **AND** the message names the file and the command that formats it

#### Scenario: Staged files outside the covered set are ignored

- **WHEN** the gate runs and the staged files include a generated Scheme file, a demo, or
  a test program
- **THEN** those files are not checked

#### Scenario: The gate is silent about unstaged work

- **WHEN** the gate runs and an unformatted covered file exists in the working tree but is
  not staged
- **THEN** the commit is permitted

#### Scenario: An absent formatter skips the gate

- **WHEN** the gate runs on a machine where the formatter is not installed
- **THEN** it reports that it is skipping, names the formatter it looked for, and permits
  the commit

### Requirement: The one-time reformat is proved semantics-preserving

The initial whole-tree reformat SHALL be shown, not asserted, to change no program's
meaning. It SHALL land as a commit containing the reformat and nothing else, so that the
evidence is not entangled with a behavioral change, and the repository SHALL record that
commit as one a line-history query ignores.

Because the committed intermediate representation carries no source-position metadata, a
reformat of the compiler's own sources SHALL reproduce the committed artifacts exactly,
with one declared exception: the artifacts that bake the prelude's *source text* into a
string constant necessarily change inside that constant. That exception SHALL be the only
difference.

#### Scenario: Regenerated compiler IR is byte-identical

- **WHEN** the covered set has been reformatted and the project's regeneration runs to its
  fixed point
- **THEN** the committed IR for the batch compiler and for every separately compiled
  runtime library is byte-identical to its pre-reformat content

#### Scenario: The embedded artifacts differ only inside the baked prelude source

- **WHEN** the reformatted tree is regenerated
- **THEN** the artifacts that embed the prelude's source text differ from their
  pre-reformat content only within that embedded string constant
- **AND** no other region of those artifacts differs

#### Scenario: Both test suites pass after the reformat

- **WHEN** the reformat and its regeneration are complete
- **THEN** the Chez-free suite and the Chez-gated developer suite both pass
- **AND** the anti-stale trust check finds the regenerated IR equal to the committed IR

#### Scenario: The reformat commit carries nothing else

- **WHEN** the reformat commit is inspected
- **THEN** every file it touches is either a covered source file whose change is purely
  layout, a regenerated artifact, or the line-history ignore list
